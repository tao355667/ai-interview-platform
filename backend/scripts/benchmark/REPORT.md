## 真实查询接口

路由：`GET /api/interview/records?page=1&page_size=10`，包含 JWT 校验、Redis 限流和真实 MySQL 的 COUNT / 分页查询，不调用 LLM。成功请求需 HTTP 200、业务 `code=200`、非空 `data`；初次抽查确认响应返回 10 条记录和总数 1,000。

| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 10 | 1 | 6,695.3 | 2.25 | 3.05 | 66,959 | 0 |
| 50 | 1 | 8,117.0 | 10.94 | 16.22 | 81,195 | 0 |
| 50 | 2 | 7,061.8 | 13.15 | 19.81 | 70,655 | 0 |
| 50 | 3 | 6,940.2 | 13.66 | 20.27 | 69,436 | 0 |
| 100 | 1 | 7,643.0 | 31.75 | 44.82 | 76,490 | 11 |

50 并发三轮累计 221,286 次成功请求、零请求错误；吞吐中位数约 7,062 次/秒。简历采用保守值：**50 并发下成功吞吐超过 6,900 次/秒、P95 小于 14ms**。100 并发时日志出现 MySQL socket `connection refused`，存在数据库连接压力，不可描述为“100 并发零错误”或“系统稳定支持万级 QPS”。

原始数据：`results/records-c*.json`。两实例 HTTP 限流单独测试 3 秒，合计 400 次 HTTP 200、65,872 次 HTTP 429；自然秒窗口跨界会覆盖 4 个窗口，此数字不能直接按 3 秒平均解释为超限。见 `results/http-shared-limit.json`。

## 跨进程额度与本次修复

使用实际 Redis Lua 滑动窗口组件，两个独立 OS 进程共享同一主体，每进程 50 并发、1,000 次请求。单轮持续约几十毫秒，未跨越一分钟的滑动窗口。

- 修复前 RPM 三轮总放行数为 **100 / 100 / 101**。第三轮 Redis 中实际仅 100 个成员，却放行 101 次。旧 ID 由时间戳和进程内计数器生成，不同进程可能产生相同成员，ZADD 覆盖会少计请求。
- 修复为每个限流实例生成 UUID 命名空间，结合实例内递增计数生成成员 ID，消除依赖跨进程时间戳唯一性的设计。
- 修复后 RPM **六轮均放行 100、拒绝 1,900，依赖错误 0**。
- TPM 三轮均在 5,000 Token 额度下允许 50 次各预占 100 Token 的请求、拒绝 1,950 次，记录用量 5,000。
- 新增 16 个独立 limiter 实例共享额度的并发回归测试；`go test -race` 通过。

原始数据：`rpm-baseline-*`、`rpm-fixed-*`、`tpm-fixed-*`。这是限流组件测试；普通 LLM 调用目前未统一接入 RPM / TPM 组件，因此不能声称所有推理请求都已获得该额度保护。

## 异步队列及并发边界

调用实际 Redis Stream、消费组、ACK 和 ants 池。处理函数仅模拟 500ms 的 I/O 等待。消息预先发布，消费计时不含发布阶段。两个消费者测试在同一 OS 进程内，各自拥有一套队列实例与协程池。

| 消费者实例数 | 消息数 | 发布耗时 | 消费耗时 | 峰值活跃处理函数 | 重复 | 结束 Pending |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 3,000 | 0.510s | 1.598s | 1,000 | 0 | 0 |
| 2 | 5,000 | 0.867s | 1.608s | 2,000 | 0 | 0 |

两个实例各处理 2,500 条消息，验证本次负载下消费组分配和每实例并发上限。不能写成每秒处理 3,000 份真实简历或支持 2,000 个同时推理的用户。

失败注入：一条消息处理失败，1.5 秒后仍为 Pending=1，无自动重试。当前实现未补齐 Pending reclaim / 死信流程，不能宣称实现宕机恢复或完整至少一次处理保障。原始数据：`queue-1.json`、`queue-2.json`、`queue-failure.json`。

## 真实模型和业务冒烟

按用户指定，从本机既有项目配置读取模型凭证；未将 Key 写入仓库或结果文件。使用 Ark / `doubao-seed-2-1-turbo-260628`。

三次顺序短问题请求均成功，首段可见内容分别耗时 **27.27s / 15.52s / 41.59s**，完整输出 **27.29s / 15.54s / 41.62s**。样本少、波动大，不作低延迟结论。见 `real-llm.json`。

真实 HTTP SSE 首题测试通过：收到 session_id、start、41 个 chunk、structured_message 和 ready_for_answer；首段内容 8.241s、进入等待回答 8.254s，主动结束 HTTP / 业务状态均为 200。见 `sse-smoke.json`。这是不同提示词的单次业务冒烟，不能与三个模型样本作优化前后对比；没有测试完整多轮面试、Milvus RAG、ASR 或并发模型请求。

## 验证与保留事项

九个相关包测试：**78 项通过、3 项跳过、0 项失败**。三个旧 Redis 集成测试因固定本机配置路径不可用而跳过；真实 Redis 另由上述双进程工具验证。限流包 race 检查与 benchmark / limiter 的 go vet 通过。见 `unit-summary.json`。

目前服务属于模块化单体；面试会话在进程内存中，session_id 使用秒级时间戳与固定后缀，尚不具备多实例会话迁移能力。以上实测支持“分布式额度一致性”和“Redis 消费组”，不支持“完整分布式微服务平台”或“高并发 AI 推理平台”。

运行用 Go 服务与独立 Redis 已在测试完成后关闭；本机 MySQL 保持运行，独立测试数据库保留供检查。含凭证的临时配置与 JWT 已清理。

## 可用于简历的项目表述

**AI 面试训练平台｜Go 后端并发与可靠性实践**

面向技术面试练习的 AI 应用，基于 Go、Hertz、Eino、Redis 和 MySQL 提供流式提问、面试记录与评估；在已有代码上开展并发问题修复、可靠性验证及性能测试。

- 针对多实例共享额度出现超额放行的问题，定位 Redis 滑动窗口成员 ID 的跨进程碰撞，改为实例 UUID＋递增计数；双进程共 100 并发、2,000 次请求，连续六轮均严格放行 100 次、拒绝 1,900 次，并补充并发回归及 race 检查。
